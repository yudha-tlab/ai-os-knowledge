## Working Principles for Main Works Profile

Prinsip kerja berikut direkomendasikan berdasarkan model bisnis TLAB (delivery berbasis project, multi-klien, integrasi sistem) dan praktik terbaik software delivery/project management:

1. **Documentation First** — setiap keputusan, requirement, atau kesepakatan dengan klien dicatat sebagai dokumen terlebih dahulu sebelum dianggap final. Rasional: TLAB mengerjakan sistem terintegrasi untuk klien institusi (universitas, enterprise) yang menuntut audit trail yang jelas.
2. **Single Source of Truth** — setiap project memiliki satu `project-profile.md` sebagai rujukan utama; tidak ada requirement atau keputusan yang hidup hanya di chat/memori.
3. **Meeting → Artifact** — setiap meeting klien wajib menghasilkan minimal satu artifact (MOM, action item, atau update requirement) sebelum meeting berikutnya dijadwalkan.
4. **Artifact → Action** — setiap dokumen (BRD/FRD/SRS) harus terhubung ke action item atau task yang dapat ditindaklanjuti tim delivery, bukan sekadar arsip.
5. **Action → Delivery** — action item dilacak sampai selesai dan dikaitkan ke milestone delivery yang dapat dilaporkan ke klien/steering committee.
6. **Traceability by Default** — requirement, desain, dan hasil pengujian saling terhubung melalui Requirement Traceability Matrix; tidak ada requirement "yatim" tanpa asal-usul atau tindak lanjut.
7. **Klien-Sentris dalam Komunikasi** — mengingat TLAB melayani klien institusi (universitas, enterprise), setiap output yang keluar ke klien (executive briefing, presentasi) harus melalui review kualitas sebelum dikirim.

## Suggested AI Operating System Principles

Rekomendasi bagaimana Hermes (profile `main-works`) mendukung kerja PM di TLAB:

1. **Project-Centric Knowledge Organization** — semua artifact (meeting, requirement, arsitektur, laporan) dikelompokkan di bawah project yang jelas, mengikuti hierarki `Project → Artifact Type → Document` yang sudah diimplementasikan di [[main-works-ai-operating-system-v1]].
2. **Meeting-Driven Workflows** — MOM sebagai titik masuk utama knowledge base; setiap meeting baru otomatis memicu pembaruan requirement/RAID log terkait, bukan proses terpisah.
3. **Document Generation dari Template** — BRD/FRD/SRS/status report/executive briefing selalu dibuat dari template baku ([[templates-hub]]) agar konsisten dan cepat dibuat lewat Telegram.
4. **Executive Reporting Otomatis** — status report mingguan dan executive briefing disusun dari data project yang sudah tercatat (RAID log, action item), bukan ditulis ulang dari nol setiap minggu.
5. **Stakeholder Management Terstruktur** — daftar stakeholder, peran, dan preferensi komunikasi per klien dicatat per-project agar komunikasi (terutama ke klien institusi seperti UGM/IPB) konsisten dan sesuai konteks masing-masing.
6. **Reusable Templates** — semua dokumen delivery memakai template versioned di `knowledge/templates/`, bukan format bebas, agar kualitas output konsisten antar project dan antar PM jika tim bertambah.
7. **Multi-Project Management** — karena TLAB melayani banyak klien sekaligus (institusi pendidikan dan bisnis), Hermes harus mampu membedakan konteks per project secara eksplisit setiap kali menerima perintah Telegram yang ambigu (tanya "project mana?" jika tidak jelas).

## Suggested Knowledge Structure

Struktur `knowledge/` saat ini (company, clients, projects, meetings, requirements, architecture, reports, presentations, templates) sudah cukup untuk delivery inti. Berdasarkan sifat bisnis TLAB (integrasi sistem, klien institusi, kemungkinan siklus sales-to-delivery penuh), folder tambahan berikut direkomendasikan bila relevan ke depannya:

| Folder Tambahan | Kegunaan | Prioritas |
|---|---|---|
| `knowledge/presales/` | Materi sebelum kontrak: kualifikasi lead, diskusi awal kebutuhan klien | Sedang — aktifkan jika PM juga terlibat di fase sebelum SPK/kontrak |
| `knowledge/proposals/` | Proposal komersial per klien (beda dengan `outputs/proposals/` yang berisi draft dokumen — folder ini untuk histori proposal yang sudah disetujui/dikirim) | Sedang |
| `knowledge/contracts/` | Ringkasan kontrak/SPK per project (bukan dokumen legal lengkap, cukup metadata: scope, durasi, nilai, milestone pembayaran) | Tinggi — penting untuk traceability delivery vs kontrak |
| `knowledge/implementation/` | Catatan teknis fase implementasi/rollout (jika berbeda dari `architecture/`) | Rendah — bisa digabung ke `architecture/` per project dulu |
| `knowledge/support/` | Log dukungan pasca-go-live per klien (tiket, SLA, eskalasi) | Sedang — relevan jika TLAB juga menangani maintenance/support klien lama seperti UGM/IPB |
| `knowledge/change-requests/` | Log permintaan perubahan scope setelah requirement disepakati | Tinggi — kritikal untuk klien institusi yang sering mengajukan perubahan di tengah project |
| `knowledge/lessons-learned/` | Retrospective per project selesai — apa yang berhasil/gagal | Sedang — bangun setelah 2-3 project pertama selesai agar tidak kosong |

**Rekomendasi implementasi:** jangan buat semua folder ini sekaligus. Tambahkan `contracts/` dan `change-requests/` terlebih dahulu (paling kritikal untuk traceability delivery TLAB), lalu tambahkan yang lain sesuai kebutuhan nyata saat project berjalan.
